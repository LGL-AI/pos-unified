# Printing and recovery

- **Receipt USB:** USB Host bulk OUT, ESC/POS raster (`GS v 0`), paper feed and full cutter (`GS V A 0`, hexadecimal `1D 56 41 00`). After PAID, this printer gets the kitchen ticket, cuts it, then gets the customer's receipt and cuts it. Android Canvas rasterizes Vietnamese and Chinese glyphs, avoiding printer code-page dependence. Receipt self-test confirms 80 mm/USB/cutter; model name is unverified. Firmware support for full cut still needs a paper test.
- **Label USB:** TSPL-compatible `SIZE`, `GAP`, `SPEED`, `BITMAP`, `PRINT`. Protocol and 203 DPI are provisional until real hardware test. Each item quantity gets its own label job; the current D1 item schema does not flag which products need labels, so the pilot labels every unit when enabled.
- **Kitchen route:** defaults to the receipt USB printer. `LAN` is an optional route to KV804 on TCP 9100, with configurable host. Select `RECEIPT_USB` for the requested two-ticket stack on one printer. Sending bytes does not prove paper physically printed.
- **Drawer:** ESC/POS pulse through receipt USB, disabled by default. It is queued only if the parent order is PAID with `paymentMethod=CASH`; split tender needs onsite validation.

The Android callback first re-reads `/api/staff/orders/{id}` with the staff session. Labels and kitchen ticket wait for the entire order to be PAID; split bill receipts print after their own bill is PAID. For a whole paid order, labels are sent to the label USB printer, the kitchen ticket is sent and cut on the receipt USB printer, then the receipt is sent and cut there. If the kitchen send fails, the receipt is held; a checked manual kitchen retry resumes the pending receipt. A local SQLite table has a unique key per document/label unit and stores `PENDING`, `PRINTING`, `SUCCESS`, `FAILED`, `UNKNOWN` or `RETRYING`, attempts and last error. A payment ID is retained before verification so a network interruption can be checked after app restart. Successful jobs never auto replay.

For a kitchen job Android claims the existing D1 `pos_kitchen_jobs` row, marks the remote state `UNKNOWN` before any device bytes, then writes and records `SENT`. This stops another terminal from reclaiming a possibly printed job. If app/device crashes while writing, local state becomes `UNKNOWN`; a person must inspect paper and retry only that job. There is no atomic confirmation from these printers that paper was produced. Manual retry is local and is **not yet an auditable manager action**. The Settings button **Giả lập PAID** renders actual ESC/POS/TSPL bytes and shows port/cut/disconnected status without writing D1 or sending to devices.
